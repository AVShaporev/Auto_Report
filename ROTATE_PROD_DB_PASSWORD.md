# Ротация пароля БД на проде 192.168.1.8

> **Что:** сменить пароль PostgreSQL-роли `autoreport` на проде 192.168.1.8 + обновить `.env` бэка + перезапустить сервис.
> **Зачем:** см. открытый пункт #14 — пароль БД на проде ни разу не ротировался с момента развёртывания. JWT `SECRET_KEY` ротирован 2026-04-18, БД-пароль остался.
> **Кто:** только админ с физическим/SSH-доступом на 192.168.1.8 и знанием пароля superuser `postgres`. Невозможно автоматизировать — пароль вводится интерактивно.
> **Окно даунтайма:** 1–2 минуты. API будет недоступен между шагом 4 («ALTER USER») и шагом 6 («systemctl restart») успешным health-чеком. Согласовать с пользователями.

---

## 0. Предусловия

Под рукой должно быть **до** начала:

- ☐ SSH-доступ на 192.168.1.8 под админ-пользователем (с `sudo`).
- ☐ Пароль superuser `postgres` (он будет нужен один раз — для подключения к psql).
- ☐ Менеджер паролей открыт и готов принять новый пароль (Bitwarden / 1Password / KeePass — где у вас прод-секреты).
- ☐ Согласованное с командой окно (1–2 минуты даунтайма).

## 1. Сгенерировать новый пароль

На своей машине (НЕ на проде, чтобы не оставлять следов в history):

```bash
openssl rand -base64 32
# пример вывода: Kj7q9V2NpR8sH4mQ1zX3bF6cT5wY0aL8eU2dM9kI7vO=
```

Скопировать в менеджер паролей **сразу**, до того как закроется терминал. Это единственный источник истины с этого момента.

> Если генерируете на Windows: `[Convert]::ToBase64String([Security.Cryptography.RandomNumberGenerator]::GetBytes(32))`.

## 2. SSH на прод и подготовительные проверки

```bash
ssh <admin>@192.168.1.8
```

Найти путь к `.env` и проверить, что systemd-сервис именно тот, который мы ожидаем:

```bash
# Имя systemd-сервиса. Подставьте реальное (auto-report.service / autoreport.service / fastapi.service — что у вас).
SVC="auto-report.service"

# 1. Где запущен и что за рабочая директория
systemctl cat "$SVC" | grep -E "WorkingDirectory|EnvironmentFile|ExecStart"
# Запомните путь к WorkingDirectory — там лежит .env.

# 2. Проверить, что сервис сейчас "running"
systemctl status "$SVC" --no-pager | head -5
```

Запишите вывод где-нибудь — `WorkingDirectory=/opt/auto-report` (или другой путь) понадобится дальше. Дальше переменная `APP_DIR` = тот самый путь:

```bash
APP_DIR=/opt/auto-report   # подставьте реальный из вывода выше
ENV_FILE="$APP_DIR/.env"
ls -la "$ENV_FILE"
# должно быть rw------- (chmod 600), owner — пользователь, под которым работает сервис
```

## 3. Бэкап перед изменениями

Делаем `pg_dump` базы — на случай, если что-то пойдёт катастрофически не так. Это **не для отката пароля** (для него хватит ALTER USER обратно), это страховка от любого сюрприза.

```bash
BACKUP_DIR="$HOME/db-backups"
mkdir -p "$BACKUP_DIR"
BACKUP_FILE="$BACKUP_DIR/autoreport-pre-pwd-rotation-$(date +%Y%m%d-%H%M%S).sql.gz"

# Под superuser postgres — он подключится через peer-auth, пароля не спросит.
sudo -u postgres pg_dump autoreport | gzip > "$BACKUP_FILE"
ls -lh "$BACKUP_FILE"
# Должен быть не пустой и не однострочный gzip-error.
```

Бэкап остаётся на сервере. Если планируете унести — `scp` его себе ПОСЛЕ успешного завершения, не до.

Бэкап текущего `.env`:

```bash
sudo cp "$ENV_FILE" "$ENV_FILE.bak.$(date +%Y%m%d-%H%M%S)"
sudo ls -la "$ENV_FILE"*
```

## 4. Сменить пароль в PostgreSQL

**Принципиальное правило:** пароль в shell history попасть не должен. Не использовать `psql -c "ALTER USER ... PASSWORD 'xxx'"` и не использовать `PGPASSWORD=...` в одной строке. Только интерактивный `\password`.

```bash
sudo -u postgres psql -d autoreport
```

Внутри psql:

```sql
-- 1. Убедиться, что мы видим нашего пользователя
\du autoreport

-- 2. Сменить ему пароль. \password — интерактивная команда psql,
--    спрашивает новый пароль ДВАЖДЫ и не отображает его на экране.
--    Под капотом отправляет ALTER USER ... PASSWORD '...' с правильным
--    хешированием (SCRAM-SHA-256) и НЕ светит пароль в логах сервера.
\password autoreport
-- Вставить новый пароль из менеджера паролей. Ввести второй раз.

-- 3. Выйти
\q
```

С этого момента **новые подключения** к БД от роли `autoreport` со старым паролем будут отбиваться. Старые активные коннекты бэка работают как работали — пока кто-то не запросит реконнект.

## 5. Обновить `.env` бэка

```bash
sudo -e "$ENV_FILE"
# Откроется редактор (vi/nano по умолчанию).
# Заменить значение DB_PASSWORD=... на новый пароль.
# Сохранить, выйти.
```

> Если `sudo -e` не работает (нет редактора по умолчанию) — `sudo nano "$ENV_FILE"` или `sudo vi "$ENV_FILE"`.

Проверить (пароль покажется в выводе — никому, кроме вас, экран не виден; завершите сессию сразу после):

```bash
sudo grep '^DB_PASSWORD=' "$ENV_FILE"
# Сверить с менеджером паролей символ в символ.
```

Права файла должны остаться прежними — `sudo -e` сохраняет владельца и права. Перепроверить:

```bash
sudo ls -la "$ENV_FILE"
# rw------- (chmod 600), owner = тот же сервисный юзер
```

## 6. Перезапустить сервис

```bash
sudo systemctl restart "$SVC"
sudo systemctl status "$SVC" --no-pager | head -10
# должно быть Active: active (running), без красного.
```

Если в выводе `failed` — **СТОП**, идти к §8 (откат). Не пытаться чинить наживую.

## 7. Проверки

```bash
# 1. Сервис жив и слушает свой порт
sudo ss -tlnp | grep -E "8000|fastapi|uvicorn"

# 2. Бэк успешно подключился к БД (в логах не должно быть FATAL: password authentication failed)
sudo journalctl -u "$SVC" -n 50 --no-pager | grep -iE "fatal|password|authentication|error"
# Норма: пусто или старые строки до restart. Если новые после restart с упоминанием password — пароль не совпал.

# 3. Внешний health-чек
curl -fsS http://127.0.0.1:8000/api/docs > /dev/null && echo "API OK"

# 4. Реальный логин (через фронт или curl)
# Подставьте имя реального пользователя и его пароль (не БД!).
curl -fsS -X POST http://127.0.0.1:8000/api/auth/login \
  -d "username=<test-user>&password=<его-пароль>" \
  -H "Content-Type: application/x-www-form-urlencoded" \
  | head -c 200
# Должен вернуться access_token. Если 500 / "could not connect to database" — пароль в .env не совпал, идти к §8.
```

Если все четыре проверки зелёные — **готово**. Переходим к §9.

## 8. Откат (если §7 показал проблему)

Сценарий: бэк не поднимается, логи `FATAL: password authentication failed for user "autoreport"`. Значит пароль в `.env` не совпал с тем, что записан в БД.

Варианты восстановления:

**Вариант А: вернуть старый пароль в БД** (быстрее всего):

```bash
sudo -u postgres psql -d autoreport
\password autoreport
# Ввести СТАРЫЙ пароль (из бэкапа .env или из менеджера паролей, если он там был).
\q

# Вернуть старый .env
sudo cp "$ENV_FILE.bak.YYYYMMDD-HHMMSS" "$ENV_FILE"   # подставить реальное имя бэкапа из шага 3
sudo systemctl restart "$SVC"
sudo systemctl status "$SVC" --no-pager | head -10
```

**Вариант Б: переписать `.env` под новый пароль** (если уверены, что в БД пароль действительно сменили правильно):

```bash
sudo -e "$ENV_FILE"
# Ещё раз сверить DB_PASSWORD с менеджером — символ в символ, без пробелов до/после, без обрезанного хвоста.
sudo systemctl restart "$SVC"
```

После любого варианта повторить §7 (все 4 проверки). Откатились — фиксируем, что попытка не удалась, разбираемся ПОЧЕМУ перед повтором (скорее всего: лишний пробел в `.env`, лишний `\n`, попавший спец-символ типа `$` в пароле без экранирования). Для пароля с `$`, `'`, `"`, `\` — либо генерируйте новый без этих символов (`openssl rand -hex 24`), либо точно знайте правила экранирования в формате вашего `.env` парсера.

## 9. Финальные шаги после успешной ротации

1. ☐ **Менеджер паролей:** новый пароль сохранён, старый помечен как "ротирован YYYY-MM-DD", не удалять минимум 7 дней (на случай отсроченных проблем).
2. ☐ **Бэкап БД с шага 3:** оставить на сервере 14 дней, потом удалить (`find ~/db-backups -mtime +14 -delete`). Если нужен off-site — `scp` себе сейчас.
3. ☐ **Бэкап `.env`** с шага 3: удалить ЧЕРЕЗ 24–48 часов (когда уверены, что новый пароль точно работает): `sudo rm "$ENV_FILE.bak.*"`. До этого момента не удалять — нужен для быстрого отката.
4. ☐ **Закрыть пункт #14** в нашем баг-листе. После закрытия его можно удалить из памяти ассистента — больше не «висит».
5. ☐ **Очистить shell history**, если случайно вводили пароль в командной строке (не должно быть, но на всякий):
   ```bash
   history | grep -iE "password|alter user|pgpassword"
   # Если что-то нашлось — `history -d <номер>` для каждой строки, потом `history -w`.
   ```
6. ☐ **Закрыть SSH-сессию** на проде, выйти из менеджера паролей.

## Чего НЕ делать

- ❌ `psql -c "ALTER USER autoreport WITH PASSWORD 'xxx'"` — пароль попадает в shell history и в `ps auxe` других пользователей в момент выполнения.
- ❌ `export PGPASSWORD=xxx` где-либо — то же самое плюс попадание в env-переменные процесса.
- ❌ Менять пароль в `.env` ДО `ALTER USER` — бэк продолжит работать со старым подключением, но при первом реконнекте упадёт с FATAL и подвиснет в restart-loop под systemd. Окно «между» должно быть в обратную сторону.
- ❌ Использовать в пароле символы `$`, `'`, `"`, `\`, `` ` `` без проверки, как ваш `.env`-парсер их интерпретирует. Pydantic Settings / python-dotenv обычно сносно жуёт значения в `KEY=value` без кавычек, но spaces / `=` / `#` ломают. Безопасный набор: `openssl rand -hex 24` даёт 48 hex-символов, никаких спецсимволов.
- ❌ Пропускать §3 (бэкап). Бэкап стоит 30 секунд, отсутствие бэкапа в критический момент — катастрофа.

## После переезда на новый VPS

См. `DEPLOY.md` §3.4 — на новом VPS пароли БД будут жить в SOPS-шифрованном `secrets/secrets.enc.yaml`, ротация делается командой `sops secrets/secrets.enc.yaml` (правка значения) + `git push` + автодеплой. Эта инструкция применима ровно до переезда; после неё пункт #14 закрывается окончательно.
